# Стек C++ (Crow) на бэкенде и Alpine.js на фронтенде

## Протоколы обмена данными в связке Crow + Alpine.js

## 1. HTTP Fetch (Периодический запрос JSON)

* **Описание**: Alpine.js по таймеру (setInterval) делает стандартный fetch('/api/metrics'). Crow обрабатывает запрос, сериализует данные в JSON и закрывает соединение.
* **Плюсы**:
  * Простейшая реализация в Crow (стандартный CROW_ROUTE) и Alpine.js.
  * Данные легко кэшируются на стороне браузера.
* **Минусы**:
  * Высокий сетевой оверхед (каждую секунду гоняются тяжелые HTTP-заголовки, тратится ресурс C++ на постоянное открытие/закрытие TCP-сессий).
* **Стратегия выбора**: Используйте для редких обновлений (раз в 1–5 секунд) и некритичных к задержкам метрик (объем диска, текущая конфигурация, лог-файлы).

## 2. Server-Sent Events (SSE)

* **Описание**: Alpine.js один раз открывает соединение через встроенный EventSource('/stream'). Crow удерживает его открытым (через stream_Route) и непрерывно «пушит» текстовые строки в одностороннем порядке.
* **Плюсы**:
  * Работает поверх стандартного HTTP (не требует настройки портов/прокси).
  * Встроенное авто-переподключение на стороне Alpine.js (если бэкенд на C++ перезагрузился, браузер сам восстановит связь).
  * Намного экономнее для процессора C++, чем Fetch.
* **Минусы**:
  * Связь строго в одну сторону. Чтобы отправить команду обратно на C++ (например, клик по кнопке), придется делать отдельный HTTP POST запрос.
* **Стратегия выбора**: Идеальная «золотая середина» для чистого мониторинга и живых графиков с частотой до 1–2 раз в секунду.

## 3. WebSockets (WS)

* **Описание**: Полноценный постоянный двусторонний (дуплексный) канал связи. Инициируется через CROW_WEBSOCKET_ROUTE.
* **Плюсы**:
  * Минимально возможная задержка (мгновенная доставка в обе стороны).
  * Нулевой сетевой оверхед после установки соединения.
  * Удобно отправлять управляющие команды обратно в C++ в том же канале.
* **Минусы**:
  * Логику переподключения при обрыве сети нужно писать руками на JS внутри Alpine.js.
* **Стратегия выбора**: Необходим при высокой частоте обновлений (10+ раз в секунду, «живые» осциллографы) или если интерфейс подразумевает интенсивное интерактивное управление устройством/сервером.

## Варианты сериализации данных внутри WebSockets

## 1. JSON

* **Описание**: Текстовый формат вида {"cpu":45, "ram":70}.
* **Плюсы**:
  * Из коробки поддерживается в JS через JSON.parse().
  * Легко читать глазами в панели разработчика.
* **Минусы**:
  * Самый медленный формат. Сборка строки в C++ (через crow::json::wvalue) и парсинг в JS нагружают процессор из-за избыточного синтаксиса (кавычки, скобки).
* **Стратегия выбора**: Подходит, если метрик немного (до 20) и частота обновлений невысокая (до 1–2 Гц).

## 2. Custom Text Format (Строка с разделителями)

* **Описание**: Текстовая строка с фиксированным порядком полей или командами (например, 45;70 или cpu:45|ram:70).
* **Плюсы**:
  * В C++ склеивается простейшей конкатенацией строк. В Alpine.js парсится мгновенно через .split(';'), что в разы быстрее, чем тяжелый JSON.parse().
* **Минусы**:
  * Хрупкая структура. При добавлении новой метрики нужно синхронно менять индексы полей и в коде C++, и на HTML-странице.
* **Стратегия выбора**: Лучший компромисс, когда нужно выжать производительность, уйти от JSON, но не хочется связываться со сложным бинарным парсингом.

## 3. Сырая C++ Структура (Raw Binary Struct)

* **Описание**: Данные упаковываются в C++ в struct с фиксированным выравниванием байт и отправляются как бинарный фрейм. Alpine читает их через DataView по смещению памяти.
* **Плюсы**:
  * Абсолютный предел скорости. Для C++ затраты процессора равны нулю (просто слепок памяти).
  * Минимальный размер пакета в байтах.
* **Минусы**:
  * Низкоуровневая магия. Малейшая ошибка в выравнивании (__attribute__((packed))) или порядке байт (Little-Endian) полностью исказит данные на клиенте.
* **Стратегия выбора**: Для экстремально высокой частоты (графики реального времени, 50+ Гц) или жестко ограниченных аппаратных ресурсов (микроконтроллеры, слабые ARM-платы).

## 4. Protocol Buffers / FlatBuffers (Protobuf)

* **Описание**: Промышленные бинарные протоколы. Схема описывается в отдельном файле, а утилита генерирует C++ класс для сервера и JS-парсер для клиента.
* **Плюсы**:
  * Строгая типизация, надежность, обратная совместимость (можно легко добавлять новые поля, не ломая старый фронтенд).
* **Минусы**:
  * Усложняет сборку C++ проекта. Требует подключения JS-библиотеки декодера внутрь страницы, что утяжеляет легковесный Alpine.js.
* **Стратегия выбора**: Для крупных диагностических панелей, где метрик сотни, они постоянно меняются, но требуется бинарная скорость и надежность.
