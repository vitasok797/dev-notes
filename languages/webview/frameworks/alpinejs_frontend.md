# Стек C++ (Crow) на бэкенде и Alpine.js на фронтенде

При проектировании обмена данными между Crow и Alpine.js полезно разделять две независимые задачи:

- **транспорт** — как данные передаются между браузером и сервером;
- **сериализация** — в каком формате данные представлены при передаче.

Для Crow практический выбор транспорта обычно сводится к HTTP-запросам и WebSocket. Формат данных выбирается отдельно и может использоваться поверх любого подходящего транспорта.

## Транспорт

### HTTP Fetch

**Описание:** Alpine.js по таймеру (`setInterval`) или по событию выполняет `fetch('/api/metrics')`. Crow обрабатывает запрос через обычный `CROW_ROUTE`, формирует ответ и возвращает данные клиенту.

**Плюсы:**

- простая реализация на стороне Crow и Alpine.js;
- подходит для редких и нерегулярных обновлений;
- удобно использовать стандартные HTTP-механизмы: коды ответа, заголовки, авторизацию, прокси и логирование;
- легко разделять API по отдельным маршрутам.

**Минусы:**

- каждый запрос содержит HTTP-заголовки и требует обработки маршрута на сервере;
- задержка обновления зависит от выбранного интервала опроса;
- для часто меняющихся метрик HTTP-кэширование обычно не требуется и должно контролироваться соответствующими заголовками.

**Когда использовать:** для редких обновлений, например раз в 1–5 секунд или реже, если небольшая задержка допустима: состояние диска, конфигурация, служебная информация, редко меняющиеся метрики.

> HTTP keep-alive позволяет переиспользовать TCP-соединение, поэтому polling не обязательно означает создание нового TCP-соединения для каждого запроса. Основные накладные расходы связаны с самим HTTP-запросом и его обработкой.

### WebSocket

**Описание:** постоянное двустороннее соединение между браузером и Crow. В Crow маршрут создается через `CROW_WEBSOCKET_ROUTE`.

**Плюсы:**

- низкая задержка доставки сообщений;
- после установки соединения накладные расходы на отдельное сообщение обычно ниже, чем у отдельного HTTP-запроса;
- один канал можно использовать и для телеметрии, и для управляющих команд;
- хорошо подходит для частых обновлений интерфейса.

**Минусы:**

- нужно отдельно реализовать переподключение после обрыва сети или перезапуска сервера;
- требуется управление жизненным циклом соединения и состоянием клиента;
- при большом числе клиентов нужно учитывать количество одновременно открытых соединений и объем передаваемых данных.

**Когда использовать:** если данные обновляются часто, нужна малая задержка или интерфейс должен активно отправлять команды обратно на сервер.

Типичные сценарии:

- телеметрия в реальном времени;
- живые графики;
- интерактивное управление устройством;
- частые события состояния;
- двусторонний обмен командами и ответами.

> Частоты вроде 10, 50 или 100 Гц сами по себе не являются жесткой границей выбора. Реальная нагрузка зависит от размера сообщений, количества клиентов, производительности устройства и сложности обработки данных.

## Сериализация

### JSON

**Описание:** текстовый формат, например:

```json
{"cpu": 45, "ram": 70}
```

**Плюсы:**

- нативно поддерживается в JavaScript через `JSON.parse()` и `JSON.stringify()`;
- хорошо читается человеком;
- удобно отлаживать в DevTools;
- структуру легко расширять новыми полями;
- прост в использовании вместе с `crow::json`.

**Минусы:**

- размер сообщения больше, чем у компактного бинарного формата;
- требуется сериализация на стороне C++ и парсинг на стороне браузера;
- при очень высокой частоте и большом объеме данных может создавать заметную дополнительную нагрузку.

**Когда использовать:** как формат по умолчанию для большинства интерфейсов мониторинга и управления. Переходить на другой формат имеет смысл только после измерения реальной нагрузки.

### Custom Text Format

**Описание:** текстовая строка с фиксированным порядком полей или простыми ключами.

Примеры:

```text
45;70
```

или:

```text
cpu:45|ram:70
```

**Плюсы:**

- очень простая реализация;
- обычно компактнее JSON;
- может быть удобен для небольшого фиксированного набора числовых значений.

**Минусы:**

- схема существует только по договоренности между сервером и клиентом;
- при изменении порядка или количества полей нужно синхронно обновлять обе стороны;
- нужно отдельно обрабатывать разделители, отсутствующие значения и ошибки формата;
- с ростом количества полей поддерживать такой формат становится сложнее.

**Когда использовать:** для небольшого стабильного набора метрик, если нужен более компактный формат, чем JSON, но полноценная бинарная схема избыточна.

> Не стоит заранее считать `.split()` гарантированно быстрее `JSON.parse()`. Для небольших сообщений разница часто несущественна. Если производительность критична, варианты нужно сравнивать на реальных данных.

### Фиксированный бинарный формат

**Описание:** сервер формирует бинарный пакет с заранее согласованной структурой полей, а браузер читает его через `ArrayBuffer` и `DataView`.

Пример логической схемы:

```text
uint16_t cpu;
uint16_t ram;
float temperature;
```

**Плюсы:**

- очень компактный размер сообщения;
- минимальные затраты на преобразование данных при простой фиксированной схеме;
- хорошо подходит для частой передачи числовой телеметрии.

**Минусы:**

- сервер и клиент должны одинаково понимать layout пакета;
- нужно явно определить размеры типов, порядок байт и смещения полей;
- нельзя безопасно полагаться на произвольный layout C++ `struct`, так как возможны padding, различия ABI и особенности компилятора;
- изменение структуры протокола требует контроля совместимости.

**Когда использовать:** для высокочастотной телеметрии или ограниченных по ресурсам устройств, если JSON уже стал измеримой проблемой по CPU, задержке или размеру трафика.

Рекомендуется описывать бинарный пакет через типы фиксированной ширины (`uint16_t`, `uint32_t`, `float` и т. п.) и явно задавать порядок байт, а не отправлять произвольный C++ `struct` как слепок памяти.

### Protocol Buffers / FlatBuffers

**Описание:** бинарные форматы со схемой данных и генерацией кода для разных языков.

**Плюсы:**

- строгая схема данных;
- хорошая масштабируемость при большом количестве полей;
- поддержка эволюции протокола и совместимости между версиями;
- компактнее типичного JSON;
- удобнее поддерживать, чем самодельный бинарный протокол, если структура данных часто меняется.

**Минусы:**

- усложняют сборку и структуру проекта;
- требуют генерации кода и дополнительных библиотек на стороне клиента и сервера;
- для небольшой панели мониторинга могут быть избыточны.

**Когда использовать:** для крупных проектов, где метрик и типов сообщений много, структура развивается со временем, а компактность и строгая схема важнее минимальной сложности реализации.

> Protocol Buffers и FlatBuffers решают похожую задачу, но устроены по-разному. Их следует рассматривать как отдельные технологии.

## Краткий выбор

| Задача | Транспорт | Сериализация |
|---|---|---|
| Редкие метрики | HTTP Fetch | JSON |
| Простая диагностическая панель | HTTP Fetch или WebSocket | JSON |
| Частые обновления интерфейса | WebSocket | JSON |
| Команды + телеметрия | WebSocket | JSON |
| Высокочастотные числовые данные | WebSocket | фиксированный бинарный формат |
| Большой развивающийся протокол | WebSocket | Protocol Buffers / FlatBuffers |

Для большинства проектов разумная последовательность такая:

1. начать с **HTTP + JSON**, если данные обновляются редко;
2. перейти на **WebSocket + JSON**, если нужен постоянный поток обновлений или двустороннее управление;
3. переходить на **Custom Text** или бинарный формат только после измерений, если JSON действительно создает заметную нагрузку;
4. использовать **Protocol Buffers / FlatBuffers**, если проект становится крупным и нужна формально описанная, версионируемая схема обмена.

Главный критерий выбора — не абстрактная максимальная скорость, а сочетание частоты обновлений, размера сообщений, количества клиентов, сложности поддержки и реальных измерений производительности.
